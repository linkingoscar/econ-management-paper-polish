# v3.1 外部项目调研报告：从“知识包”走向可验证的论文写作工作流

> 状态：提案阶段（不代表 v3.1 已经实现）
> 调研日期：2026-08-03
> 调研对象：公开 GitHub 仓库、README、架构/设计文档、脚本、schema、测试与评测说明
> 服务项目：`econ-management-paper-polish` v3.0.0-alpha.1
> 本地工作原则：本报告只提出兼容 v3.0 的升级设计，不自动复制第三方代码、提示词、论文语料或不可验证的性能宣传。

## 0. 先给结论

外部生态已经从“一个很长的 `SKILL.md`”明显转向四种工程化形态：

1. **全流程编排器**：把 research、write、review、revise、finalize 拆成可暂停的阶段，并在阶段之间传递结构化产物。
2. **领域知识包**：把方法、写作、审稿标准拆成可路由、可替换、可评测的 collection，而不是一次加载全部规则。
3. **证据与审计系统**：用 Material Passport、证据账本、issue ledger、anchor diff、compile guard 等对象记录“为什么能改、改了什么、如何验证”。
4. **按需分发和安全边界**：使用 manifest、版本锁、能力声明、安装器和离线优先工作区，避免把一百多个技能和未知脚本一股脑注入代理上下文。

这给 v3.1 的启示不是“再增加几十个模块”，而是建立四条写作主线：

* **证据主线**：检索 → 去重 → 证据定位 → 主张绑定 → 综合，为论文写作形成持久化证据图。
* **写作主线**：目标期刊语料 → style card → 冲突消解后的动态写作规则 → 单节修订日志。
* **审稿主线**：问题提出 → 分诊 → 裁决 → 有界修改 → 确定性验证，默认保留作者决策点。
* **交付主线**：技能来源、权限、版本、依赖、评测和退化模式均可声明、可锁定、可审计。

v3.0 已有路由卡、证据包、确定性审计、方法安全层和 14 个职责化 reference 包；v3.1 应优先补上**持久化写作状态、语料驱动期刊适配、问题生命周期、写作证据深度、方法写作评测与安全交付**，而不是重新堆叠知识文件。

### 1.2 证据分级

本报告将结论分成三类，避免把 README 的自我描述误写成已经验证的事实：

* **观察事实**：在公开仓库的 README、目录、脚本、schema 或测试中可以直接定位到的内容。
* **项目自报**：仓库声称的技能数量、agent 数量、star、吞吐量或成本；这些数字只用于了解生态规模，不等于本项目的质量结论。
* **工程推断**：结合 v3.0 现状和外部模式提出的设计建议，需要在 v3.1 实现后用本项目自己的 fixtures、日志和 benchmark 验证。

GitHub star、fork、最近推送时间按 2026-08-03 的 GitHub API 快照记录；它们是活跃度线索，不是学术正确性、代码安全性或方法质量的替代指标。

## 3. 深度观察：哪些设计值得借鉴

### 3.1 全流程套件：阶段产物比“更多 agent”更有价值

[academic-research-skills](https://github.com/Imbad0202/academic-research-skills) 把研究拆成独立入口和阶段，并在其架构文档中使用 Material Passport、语料优先/搜索补缺、引用验证缓存、阶段确认和可恢复状态。其 README 还给出了完整流水线的高 token 消耗估计；这是项目自报的容量提示，不应被当作跨模型 benchmark。

可迁移到 v3.1 的不是 12/13/7 个 agent 这个数字，而是下面的契约：

1. 每个阶段有明确输入、输出、阻塞条件和人工确认点。
2. 阶段之间传递 YAML/JSON 产物，而不是把上一阶段的长文本重新塞进上下文。
3. 语料、引用、拒收原因和来源哈希一起进入 passport，换会话仍能复核。
4. 长流程可以从最后一个通过的 gate 恢复，失败不要求从头重跑。
5. 没有 PDF、网络、凭据或可用模型时，输出能力声明和降级结果，而不是伪装完成。

v3.1 计划将这些原则压缩为 `paper-spine.yaml`、`corpus-manifest.yaml`、`evidence-ledger.jsonl`、`review-ledger.jsonl`、`repro-lock.yaml` 五类状态对象。默认串行；只有在任务被标记为 `bounded_parallel` 时才开启受上限控制的并行角色。

### 3.2 大型技能生态：用 router 和 manifest 控制规模

[scientific-agent-skills](https://github.com/K-Dense-AI/scientific-agent-skills) 与 [AI-Research-SKILLs](https://github.com/Orchestra-Research/AI-Research-SKILLs) 证明了“技能生态”的发现、安装、版本锁定和多平台入口很重要。但它们的广度也暴露了风险：

* collection 越多，越需要冲突优先级和适用域标签；
* 数据库和脚本越多，供应链、网络权限和凭据泄露面越大；
* 全量注入会消耗上下文，并让不相关的规则互相污染；
* ML/生物/化学场景的默认假设不能直接用于经济管理识别设计。

v3.1 因此只借鉴三件事：`skill-manifest`、按需 router、锁定/安全扫描；不复制大规模 skill 文本。所有外部 adapter 需要声明来源 commit、许可证、网络/文件/命令能力、测试状态和撤销方式。

### 3.3 自动实证研究：方法覆盖必须和 benchmark 绑定

[Auto-Empirical-Research-Skills](https://github.com/brycewang-stanford/Auto-Empirical-Research-Skills) 的公开说明把方法 collection、语言/工具链和评测场景放在同一项目中，并强调 router 不会一次加载全部 collection。这比“列出更多方法名”更值得借鉴。

v3.0 已覆盖 DID、IV、RD、面板、调查、实验、定性研究。v3.1 应扩展为**方法风险卡 + fixture + 负例**三件套：

* 风险卡说明数据结构、识别变异、目标估计量、关键假设、诊断、不能解决的问题和报告要求；
* fixture 刻意植入错误（把 event-study 当作平行趋势证明、把 PSM 写成解决内生性、把异质性处理效应当成单一 ATT 等）；
* benchmark 测“是否识别了风险并保守表述”，而不是测模型能否生成漂亮的方法段落。

### 3.4 经济学写作：把“写得像论文”与“方法说得对”分开

[econ-writing-skill](https://github.com/hanlulong/econ-writing-skill) 的识别策略文档和 review checklist 特别适合补强 v3.0：它把识别策略、经济意义、外部有效性、主张—证据匹配和审稿人角色放在一起，同时对 DiD、IV、RDD、Bartik、合成控制、bunching、结构估计等方法给出独立说明。

借鉴边界：

* 可借鉴方法分类、红线、检查项和 rubric 结构；
* 不直接复制第三方长篇指南，不把其默认期刊或美国经济学写作规范当成中文管理学通用规则；
* 任何新方法仍需绑定本项目的权威来源、版本和核验日期；
* “经济显著性”应成为结果审计字段，而不是一句可选的写作建议。

### 3.5 期刊动态适配：journal card 还不够

[journal-adapt-writing-skill](https://github.com/WantongC/journal-adapt-writing-skill) 的关键贡献是把目标期刊适配变为一个两阶段流程：先分析目标期刊、领域/主题和用户示例，生成 style cards 与聚合 profile；人工确认后，再用 dynamic writing skill 修订指定章节。它明确了优先级：

`P1 事实/引用/方程/符号/数字保留 > P2 目标期刊 > P3 次级语料 > P4 静态规则 > P5 清理`。

v3.1 应照搬这个**优先级思想**，但把“风格”限定在结构、修辞动作、段落长度、图表引入方式和论证节奏，明确禁止：

* 从语料复制句子、独特比喻、发现、结论或引用段落；
* 用期刊语料覆盖用户真实结果、变量含义或识别假设；
* 把小样本、过期指南或单一作者样本提升为硬性规则。

### 3.6 PaperJury：v3.1 的问题账本应从一开始就是事实源

[paperjury](https://github.com/u7079256/paperjury) 的仓库结构提供了很强的工程参考：工作流、`scripts/`、ledger schema、compile guard、anchor diff、meaning audit、recall audit、测试和 dogfood 样例分离。其核心状态不是“审稿意见列表”，而是可裁决的 issue：

* `safe-fix`：机械或低风险，满足保护条件后可自动处理；
* `author-required`：需要作者判断、数据或理论选择；
* `invalid`：证据不足或问题不成立；
* 后续必须经过 apply、verify 和 gate，而不是修改后就默认关闭。

v3.1 不会直接实现其所有 reviewer persona，而是先引入 `review-ledger.jsonl`，把每条问题的来源、证据、风险、拟议动作、权限和验证结果写全。Markdown 视图可以生成，但 JSONL/JSON 才是事实源。

### 3.7 写作质检：引入 rhetorical moves 和独立 red team

[paper-writing-skill](https://github.com/SNL-UCSB/paper-writing-skill) 公开了 Draft 0、逆向提纲、claim-evidence 对齐、section rhetorical moves、figure specification、independent red team 等结构。它的项目自报数据来自 Overleaf 编辑历史和多轮审稿，不是普适科学结论；但这些对象对经管论文仍然有用：

* 每段应有可标注的动作：设定问题、定位缺口、提出机制、给出识别、解释结果、限定外推；
* 图表应先有“要证明什么”的 figure spec，再检查是否支持主张；
* 由独立 reviewer 只看主张和证据，不复述作者原来的解释；
* 压缩前保留论证骨架，避免语言优化误删识别条件。

### 3.8 深度研究与中文生态：检索 provider 与交付层分离

[Deep-Research-skills](https://github.com/Weizhena/Deep-Research-skills) 和 [agent-research-skills](https://github.com/lingzhi227/agent-research-skills) 展示了 outline/deep investigation、并行检索、PDF 提取、BibTeX、报告生成等流程；[codex-claude-academic-skills](https://github.com/zLanqing/codex-claude-academic-skills) 说明中文研究写作、Office 和科学工具可以共用一致的跨代理入口。

v3.1 的实现边界是：

* 现有 Crossref/OpenAlex 适配器保留；新增 provider 采用统一的 `search → normalize → dedupe → verify → cite` 接口；
* PDF 解析、BibTeX、Zotero/Obsidian 等均为可选 adapter，失败时回退到元数据级证据；
* 中文/英文是交付语言参数，不改变证据、方法和保留原则；
* 不声称能够访问 CNKI、付费全文或原始数据，除非用户明确提供可读文件/凭据并且能力卡标注为 Verified。

### 3.9 分发与工作区：把安装当成供应链问题

[AcademicForge](https://github.com/HughYau/AcademicForge) 的按需 picker、[claude-prism](https://github.com/delibae/claude-prism) 的离线写作工作区，以及大型技能项目的 lock/install 文档共同指向一个趋势：用户要的是可安装、可更新、可回滚的产品，而不是复制一段提示词。

v3.1 需要最小化实现：

* `skill-manifest.json`：版本、来源、许可证、依赖、能力和测试状态；
* `repro-lock.yaml`：本项目自身及可选 adapter 的 commit/hash；
* `scripts/check_skill_provenance.py`：检测缺失来源、未声明能力和许可证字段；
* 默认离线运行；网络、Shell、外部模型和文件写入全部显式声明。

## 4. v3.0 与代表项目的差异矩阵

| 能力维度 | v3.0 现状 | 外部最佳模式 | 差距判断 | v3.1 决策 |
|---|---|---|---|---|

| 方法安全 | 覆盖核心设计并强调不越界 | 更细的 collection、负例和 benchmark | 中高 | P0：扩展方法卡 + 评测 fixture |

| 修改安全 | 有数字/变量/引用/LaTeX 审计 | anchor diff、compile guard、meaning audit | 中 | P0：patch 前后硬保护 + 高风险转作者 |
| 多代理 | 已有串行/HTTP 适配器 | 角色分工、上下文隔离、门控、预算和重试 | 中 | P1：bounded parallel，不追求 agent 数量 |
| 检索深度 | Crossref/OpenAlex + 本地 RAG | 多 provider、PDF/BibTeX、并行研究、缓存 | 中高 | P1：统一 provider 接口和离线降级 |
| 评测 | smoke/extended fixtures 与 CI | gold set、mutation、benchmark、security scan | 高 | P0：方法/证据/修改/安全四类 benchmark |
| 可移植性 | 多代理入口已文档化 | manifest、安装器、锁定、按需加载 | 中 | P1：能力和来源 manifest |
| 许可证/供应链 | MIT 项目自身，外部借鉴未结构化 | 每个 skill/adapter 有 provenance 与 license | 中高 | P0：不 vendoring；来源/许可证检查 |
| 工作区 | 状态 schema 存在，用户需手工组织 | 离线项目目录、恢复、预览、日志 | 中 | P1：标准 `paper-workspace/` 目录 |

## 5. 明确不照搬的做法

### 5.1 不用 star 或 skill 数量替代质量

大型仓库的 star 只能表示关注度。v3.1 的接受标准必须来自本项目的负例、确定性检查、证据追踪、人工抽查和回归测试。

### 5.2 不把“自动研究循环”设为默认

自动循环会放大错误检索、重复调用和 token 消耗。默认模式应为 `serial`；`bounded_parallel` 和 `full_pipeline` 必须明确开启，并有最大 agent 数、最大重试数、最大文献数、最大字符数和超时。

### 5.3 不把期刊语料变成抄袭引擎

动态适配只提取结构/修辞统计和可解释规则，不保存或生成可替换的原句库。所有语料都写入来源、用途、哈希和删除/过期策略。

### 5.4 不让模型做本可确定性完成的检查

数字、变量名、表图交叉引用、BibTeX/DOI、LaTeX 编译和 patch anchor 继续由脚本负责；模型只负责语义判断、解释和候选修复。

### 5.5 不复制第三方代码、提示词和未声明许可证内容

借鉴接口、流程和公开方法；不将外部 repo 的 `SKILL.md`、论文语料或脚本直接 vendored 进本项目。需要 adapter 时，保留独立来源和 license manifest。

### 5.6 不提供 AI 检测规避

相邻项目可能把“humanizer”作为流量入口；v3.1 只做具体性、作者声音、论证清晰度和模板化语言 lint，不优化“无法被检测”或伪造作者身份。

## 6. v3.1 的优先级决策

### P0：必须先做

1. `corpus-manifest`、`style-card`、`style-profile` 和动态期刊适配的两阶段 gate。
2. `evidence-ledger` 持久化、来源 locator、拒收日志、过期状态和 claim/source 绑定。
3. `review-ledger` 状态机、裁决、bounded patch、anchor/compile/meaning/recall gate。
4. 扩展方法安全卡和负例 benchmark，覆盖分期 DID、连续处理、Bartik、CATE、mediation、quantile/Oaxaca 等优先方法。
5. benchmark schema、mutation tests、provenance/security scan 和 v3 回归门槛。

### P1：完成 P0 后做

1. Semantic Scholar、OpenAlex、Crossref、arXiv、RePEc/IDEAS 等 provider 的统一接口；付费数据库和 CNKI 仅保留 adapter 位置，不虚构可用性。
2. Zotero/BibTeX/文件夹/Obsidian 等 corpus adapter，统一输出 manifest 和 rejection log。
3. bounded parallel 多代理编排、预算遥测、重试/取消/恢复。
4. 标准 `paper-workspace/`、Markdown 报告视图、HTML/PDF 预览和差异报告。

### P2：验证需求后再做

1. 跨模型交叉验证和自动 reviewer ensemble。
2. 更广的中文核心/英文商科期刊 style profile 库。
3. 结构估计、机器学习因果、混合方法等更深 collection。
4. 图表视觉审计、表格 OCR、复杂 Word 版式复现。

## 7. 关键设计决定（供 v3.1 实现时引用）

| 决定 | 选择 | 理由 |
|---|---|---|
| 事实源 | JSON/JSONL ledger，Markdown 为派生视图 | 可合并、可 diff、可审计；避免手工表格与运行时状态分叉 |
| 默认执行 | 串行 + 阶段 gate | 控制 token、减少规则冲突、适合作者逐步确认 |
| 自动修改 | 仅低风险、保护条件通过的 safe-fix | 高风险主张/识别/理论选择必须交给作者 |
| 期刊适配 | 语料分析与修订分两阶段 | 修订时不反复加载整套语料，减少上下文和抄袭风险 |
| 方法建议 | 数据结构 → 识别变异 → 估计量 → 假设 → 威胁 → 方法 → 不能解决 → 报告 | 约束模型不能从方法名称直接跳到结论 |
| 外部技能 | adapter + manifest，不 vendoring | 维护许可证、更新、撤销和安全边界 |
| 能力声明 | Verified / Documented / Conceptual + 权限清单 | “支持”必须区分已测、可安装和仅设计 |
| 评测目标 | 以错误拦截、证据追踪、保留率和降级诚实度为主 | 不用流畅度掩盖学术风险 |

## 9. 对本项目下一步的直接要求

在实现 v3.1 之前，任何新功能都应先回答四个问题：

1. 它会产生哪一个可持久化 artifact？
2. 它由哪条确定性检查或人工 gate 负责验收？
3. 它失败时如何降级，是否会让用户误以为已完成全文/因果/复现？
4. 它是否改变了数字、变量、引用、公式、作者主张或语料版权边界？

如果四个问题答不清楚，功能应留在 v3.1 设计文档，不应直接加入 `SKILL.md` 或 README 的“已支持”列表。

## 10. 写作 Skill 的范围校正

本项目的第一性目标是**帮助作者写清楚、改准确、投得合适、返修可追踪**。因此，上述外部项目不能按“谁的技能/agent/数据库更多”来排序，而要按它们是否直接改善论文写作来筛选。

### 10.1 四条写作主线

1. **表达主线**：句子、段落、章节、图表说明和中英文风格。
2. **论证主线**：研究问题、理论机制、假设、识别、结果解释、贡献和局限之间的衔接。
3. **证据主线**：引用、方法文献、政策背景、期刊规则与具体主张的可追溯绑定。
4. **返修主线**：审稿意见、作者回应、修改动作、风险和验证结果的闭环。

研究检索、RAG、PDF 解析、多代理和语料管理都只是这四条写作主线的基础设施。它们只有在能够减少虚构引用、改善论证、保护作者结果或提高返修可核验性时，才进入 v3.1；不会因为“生态中存在”就自动成为本项目功能。

### 10.2 代表项目的写作相关性重排

| 优先级 | 项目 | 借鉴内容 | 明确不借鉴 |
|---|---|---|---|
| P0 | econ-writing-skill | 经济学识别策略写作、claim–evidence、经济意义和 reviewer rubric | 不复制长篇指南，不把经济学规则硬套到管理学 |
| P0 | journal-adapt-writing-skill | 目标期刊语料、style card、动态写作规则、P1 事实保留和人工 gate | 不做原句检索/仿写，不把样本风格当硬规范 |
| P0 | PaperJury | 返修 issue 生命周期、风险分级、bounded patch、验证与回滚 | 不让审稿 agent 代替作者决定理论或结果 |
| P0 | SNL-UCSB/paper-writing-skill | rhetorical moves、逆向提纲、red team、图表论证 | 不把 ML/CV 的章节套路直接迁移 |
| P1 | academic-research-skills | 阶段门控、证据护照、可恢复写作上下文 | 不复制大规模 agent 队伍和高 token 全流程 |
| P1 | Deep-Research-skills / agent-research-skills | 为文献补强提供 outline、检索、去重和报告接口 | 不把本项目扩成自主研究代理 |
| P1 | Auto-Empirical-Research-Skills | 方法 collection/router/benchmark 思路，用于方法段落安全 | 不追求 1,000+ skill 规模 |
| P2 | K-Dense / Orchestra / AcademicForge | 按需加载、manifest、版本/权限声明 | 不把通用科学技能生态 vendored 进写作 Skill |
| P2 | claude-prism / 中文生态项目 | 离线工作区、中文交付、跨代理入口 | 不把 Office/通用科学工具当核心路线 |

### 10.3 对 v3.1 的结果

v3.1 的发布标题和 README 应使用“写作可靠性与返修闭环”，而不是“自主科研平台”。P0 只包含动态期刊适配、论点—证据诊断、方法安全改写、审稿/返修账本、受保护修改和写作评测；provider、广泛语料导入和 bounded parallel 属于 P1/P2，必须以写作收益为验收条件。
